Concepto 1 · el otro servidor no es suyo

Siempre con timeout: esperar, sí; esperar para siempre, no

La analogía

Pedir un dato por teléfono

Un cliente le pregunta algo; usted llama a otra oficina para averiguarlo. Si nadie contesta en 30 segundos, cuelga y le dice al cliente “ahorita no puedo, intente más tarde”.

Lo que no hace es quedarse con el teléfono pegado una hora mientras la fila de clientes crece.

En su API

Toda llamada remota lleva timeout

Amazon: “una práctica recomendada… consiste en establecer un tiempo de espera para cualquier llamada remota”.

Si el externo no contesta a tiempo, su API responde 504 Gateway Timeout. Si contesta mal, 502 Bad Gateway. Nunca un 500 ni un usuario esperando sin saber.

Cómo lo vamos a probar: su API lee la dirección del servicio externo de una variable de entorno, EXTERNO_URL. Para las pruebas la apuntamos al simulador (http://127.0.0.1:9000), que reenvía al servicio real… o falla a propósito cuando se lo pedimos. En la industria se usan herramientas así (por ejemplo, Toxiproxy).
Brooker, M. (s.f.), Timeouts, retries, and backoff with jitter. Amazon Builders’ Library

Concepto 2 · reintentar sí, pero con criterio

Solo lo pasajero, y esperando cada vez un poco más

✓ Se reintenta (puede arreglarse solo)

Timeout / sin conexiónel otro está lento o se reinició
429 Too Many Requestsvas muy rápido: espera lo que diga Retry-After
500 · 502 · 503 · 504falla del otro lado, a veces momentánea

✗ No se reintenta (seguirá igual)

400 · 422lo que mandaste está mal
401 · 403tu clave no sirve o no tiene permiso
404eso no existe
Backoff: esperar 0.5 s, luego 1 s, luego 2 s… y rendirse (3 intentos en el ejemplo). Amazon: “los reintentos son egoístas”: si el otro está saturado, reintentar de inmediato lo empeora.
Jitter: sumar un poco de azar a la espera. Si mil clientes fallan a la vez y todos reintentan exactamente al segundo, vuelven a chocar juntos. El azar “distribuye los reintentos en el tiempo”.
Brooker, M. (s.f.), Amazon Builders’ Library · los números (0.5 s, 3 intentos) son del ejemplo; cada sistema elige los suyos

Concepto 3 · la idempotencia de la sesión 1, ahora en serio

Cuando el reintento hace daño: el correo sí salió

1Su API pide: “manda el correo del préstamo 41”.
2El servicio sí lo manda… pero su respuesta tarda.
3Su API llega a su timeout: no sabe si salió.
4Reintenta: segundo correo. Con un cobro, segundo cargo.
La solución: mandar el encabezado Idempotency-Key con la misma llave en todos los intentos (por ejemplo prestamo-41). El servicio recuerda las llaves: si ve una repetida, regresa la respuesta de la primera vez y no repite la acción.
Stripe lo hace así con los cobros, y AWS con muchas de sus APIs. Es la frase de la sesión 1: “1 vez o 10 veces, los datos terminan igual”. Con llave, reintentar se vuelve seguro.
Stripe (s.f.), Idempotent requests · Featonby, M. (s.f.), Making retries safe with idempotent APIs

Concepto 4 · la IA es una API HTTP más… con trampas propias

Una petición POST con texto; una respuesta JSON que hay que revisar

POST https://generativelanguage.googleapis.com /v1beta/models/gemini-flash-lite-latest:generateContent x-goog-api-key: (de la variable GEMINI_API_KEY) {"contents": [{"parts": [{"text": "Clasifica... responde SOLO un JSON {gravedad, resumen}. Reporte: ..."}]}], "generationConfig": {"responseMimeType": "application/json"}} # respuesta: el texto viene aquí adentro candidates[0].content.parts[0].text → '{"gravedad": "alta", "resumen": "..."}'
No es determinista. La misma pregunta puede dar respuestas distintas, o un JSON incompleto. Validen cada campo, como si lo mandara un usuario.
Cobra y limita. Se paga por tokens; el nivel gratuito tiene límite por minuto: 429.
Tarda segundos. Mucho más que su base de datos: timeout y mensaje claro.
Se lleva lo que le manden. Nada de contraseñas ni datos personales en el prompt: solo lo necesario.
Google (s.f.), Gemini API · el modelo se configura con GEMINI_MODELO: los nombres cambian con frecuencia
Regla 4 · la API key es una contraseña con tarjeta de crédito

La clave vive en una variable de entorno, nunca en el código

✗ Así se filtran

GEMINI_API_KEY = "AIzaSyD...la clave real" # git add . && git push → pública para siempre # en el front (JavaScript): cualquiera la ve con F12

✓ Así

# el código solo la LEE GEMINI_API_KEY = os.environ.get("GEMINI_API_KEY", "") # Windows: variables de entorno (o un archivo .env # que está en .gitignore y nunca se sube)
La prueba de los doce factores: ¿podrían publicar su código hoy mismo “sin comprometer ninguna credencial”? Si la respuesta es no, hay una clave donde no debe.
El front nunca llama a la IA directo: llama a su API, y su API (en el servidor) llama a la IA con la clave. Si una clave se filtra: revóquenla y generen otra, no basta con borrarla del repositorio.

Así se ve en el código · llamar_externo() en api_equipos.py

Una función para todas las llamadas externas

def llamar_externo(metodo, url, cuerpo=None, encabezados=None, llave=None): for intento in range(1, INTENTOS + 1): # INTENTOS = 3 req = urllib.request.Request(url, data=..., method=metodo) if llave: req.add_header("Idempotency-Key", llave) # misma llave en cada intento try: with urllib.request.urlopen(req, timeout=TIMEOUT) as r: # TIMEOUT = 2 s estado, texto = r.status, r.read() except urllib.error.HTTPError as e: estado, texto = e.code, e.read() except (URLError, socket.timeout, ...): estado, texto = None, b"" # no contestó a tiempo if estado is not None and estado not in {429, 500, 502, 503, 504}: break # éxito, o un error que NO se reintenta if intento < INTENTOS: time.sleep(0.5 * 2 ** (intento - 1) + random.uniform(0, 0.2)) # backoff + jitter if estado is None: raise HTTPException(504, "El servicio externo no respondió a tiempo") if estado >= 400: raise HTTPException(502, "El servicio externo falló o rechazó la petición") try: return json.loads(texto) # validar: ¿de verdad es JSON? except ValueError: raise HTTPException(502, "El servicio externo respondió algo que no es JSON")

Después, reportar_falla() valida que la IA haya respondido gravedad en {alta, media, baja}. Si no: 502. ámbar = las 4 reglas

Para no llegar novatos · preguntas típicas de una entrevista de backend

Después de hoy, ya las pueden contestar

“¿Qué haces si el servicio del que depende tu API se cae o tarda?”Timeout en cada llamada, reintentos solo en fallas pasajeras con backoff y jitter, y si no se recupera, 502/504 claros: mi API no se cae con él.
“¿Siempre reintentas?”No: un 400 o un 404 no se arreglan solos. Y si la operación tiene efectos (cobrar, enviar), solo con Idempotency-Key.
“¿Dónde guardas las API keys?”En variables de entorno o un gestor de secretos; nunca en el repositorio ni en el front. Si se filtra, se revoca.
“¿Qué cuidas al integrar un modelo de IA?”Validar su salida porque no es determinista, timeouts, límites y costo por tokens, y no mandarle datos personales.
“¿502 o 504?”502: el servidor del que dependo respondió algo inválido o un error. 504: no respondió a tiempo.

Cierre · el gancho

¿Qué ve el usuario? Debería ser la B.

Sin timeout, pasa la A en el mejor caso… y la C en el peor: cada petición que espera ocupa a su servidor, y con suficientes peticiones esperando, nadie más es atendido. Con timeout, reintentos con criterio y un 504 claro, el usuario recibe la B en pocos segundos.

¿Cuántos votaron por la A pensando “es lento pero funciona”?

Llévense esto

  • Toda llamada remota lleva timeout.
  • Se reintenta solo lo pasajero, esperando más cada vez.
  • Si reintentar puede duplicar algo: Idempotency-Key.
  • Lo que llega de afuera se valida; las claves viven fuera del código.
